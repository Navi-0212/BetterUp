## 1. BUSINESS CONTEXT

BetterUp's onboarding coordination spans five systems with no single
source of truth:

- Ashby        — ATS. Source of truth BEFORE the hire (offer, name, start
                 date, address).
- Workday      — HRIS. System of record AFTER the hire. Can also receive
                 off-cycle hires created directly, bypassing Ashby.
- Okta         — Identity/SSO. Owns login + auth.
- Lumos        — Sits on top of Okta. Governs app access, driven by HRIS
                 lifecycle events (joiner/mover/leaver).
- expoIT       — IT hardware vendor/reseller. Ships the laptop; needs a
                 correct shipping address.
- Cohort tracker — Internal checklist/status system humans read.

Three failure modes result:

1. CHANGE PROPAGATION — a name/start-date/address change after the offer,
   or an off-cycle hire outside Ashby, never ripples downstream.
2. BAD DATA CASCADES — wrong name/address in Ashby flows straight into
   Workday, the Okta email, and the shipping label unchecked.
3. NOBODY'S WATCHING THE GATES — hardware form, background check, Okta
   provisioning have ~7-day deadlines nobody tracks.


## 2. CHOSEN SLICE — AND WHY (defend this in the debrief)

Building: CHANGE PROPAGATION, with validation nested inline (validated at
the moment a field is transformed for a downstream write, not as a
separate system), and a thin exception-monitoring read endpoint as a
stretch goal over the same state store.

- Only slice that forces a canonical data model, a diffing mechanism, and
  per-system idempotent writes — the actual engineering depth being
  graded.
- Validation is nearly free once propagation exists: validate as you
  transform, before you write.
- Exception monitoring is a read-only view over state propagation already
  maintains — cheap to bolt on last, not worth building first.
- The only slice where an LLM has a legitimate job: resolving genuinely
  ambiguous cases (Section 10), not gluing systems together.


## 3. THE OFF-CYCLE / NO-SINGLE-SOURCE-OF-TRUTH PROBLEM

Ashby is authoritative pre-hire, Workday post-hire. An off-cycle hire can
appear in Workday with no Ashby record at all. Design decision (state
explicitly in build_note.md): when no Ashby record exists for an
employee_id, Workday is authoritative for that record, tagged
`source_system=WORKDAY_OFFCYCLE`. Do not reconstruct a fictitious Ashby
record.

## 6. SYSTEM ARCHITECTURE

```
ChangeEvent (sample_events/*.json, simulating an Ashby webhook or
             Workday off-cycle detection)
        |
        v
  normalize_event()   -> candidate Employee (see Section 8 signature)
        |
        v
  find_near_duplicate()  -> checks for an ambiguous match against the
                             state store (Section 10's deterministic
                             pre-filter, NOT every event goes through Claude)
        |
        v
  IF near-duplicate found -> claude_handler.resolve_conflict()
        -> log CLAUDE_CONFLICT_RESOLVED or NEEDS_HUMAN_REVIEW
        -> low confidence / parse failure forces needs_human_review
        |
        v
  validate_fields()   -> per-field validation; a bad field is dropped
                          (VALIDATION_REJECTED), not the whole event
        |
        v
  fan out valid changed fields to per-system transformers
        (transform_for_workday / okta / lumos / expoit / tracker)
        |
        v
  write_with_retry() per system, per field-group — isolated failures
        |
        v
  audit_log.append()
```

## 9. IDEMPOTENCY & FAILURE HANDLING (must be enforced, will be tested)

- `idempotency_key = sha256(f"{employee_id}:{field_name}:{new_value}:{target_system}")`
- Before writing: if a `LedgerEntry` with this exact key already has
  status `ACKED`, skip the write and log a no-op — replaying an event must
  not double-ship a laptop or double-fire an Okta update.
- Each connector write is wrapped individually (`try/except` per system,
  per field-group). A failure in one system must not block another's
  write from being attempted.
- Retry formula: `delay = 0.1 * (2 ** attempt_number)` seconds, up to
  `max_attempts=3`, called via the injectable `sleep_fn` from Section 8 —
  tests pass `sleep_fn=lambda _: None` so the suite runs instantly. After
  3 failures, status becomes `FAILED` and the entry surfaces via
  `StateStore.needs_attention()`.
- REQUIRED TEST (`test_idempotency.py`): process `name_change.json` twice.
  Assert each mock connector's `write()` was called with a real attempt
  exactly once (second run short-circuits on the ACKED ledger check).
- REQUIRED TEST (`test_partial_failure.py`): `fake_expoit.py` raises
  deterministically for `employee_id == "emp_offcycle_test"`. Assert
  Workday/Okta still reach `ACKED` while expoIT reaches `FAILED` after 3
  attempts, and appears in `needs_attention()`.


## 10. VALIDATION RULES + NEAR-DUPLICATE ALGORITHM (deterministic — no LLM call here)

Field validation (`validate_fields`), applied before fan-out:
- `legal_first_name` / `legal_last_name`: non-empty after strip, no
  digits.
- `address`: all of line1/city/state/postal_code/country non-empty.
- `start_date`: not before `event.received_at` (calendar date comparison).
A rejected field is dropped (`VALIDATION_REJECTED` in the audit log with
the reason); the rest of the event's valid fields still propagate.

Near-duplicate pre-filter (`is_near_duplicate`) — stdlib only, no new
dependency:
```python
from difflib import SequenceMatcher

def is_near_duplicate(candidate: Employee, existing: Employee) -> bool:
    if candidate.employee_id == existing.employee_id:
        return False  # same record, not a conflict
    if candidate.start_date != existing.start_date:
        return False  # different start dates -> not the same hire
    name_a = f"{candidate.legal_first_name} {candidate.legal_last_name}".lower().strip()
    name_b = f"{existing.legal_first_name} {existing.legal_last_name}".lower().strip()
    if name_a == name_b:
        return False  # exact match is a normal update, not an ambiguous conflict
    ratio = SequenceMatcher(None, name_a, name_b).ratio()
    return ratio >= 0.75
```
This pre-filter runs against every existing employee in the store BEFORE
any Claude call — Claude is only invoked when this returns `True` for at
least one existing record. This is what keeps the LLM call rare and
justified rather than a call-per-event router.


## 11. CLAUDE INTEGRATION (claude_handler.py)

Triggered only when `is_near_duplicate()` finds a candidate match
(Section 10) — never on ordinary field changes.

Exact prompt (system + user), sent via the Messages API:

**System:**
```
You are resolving a data conflict for an HR onboarding sync system. You
will be given two employee records that a deterministic name-similarity
check flagged as a possible match. Decide whether they are the same
person, different people, or too ambiguous to auto-decide. Respond with
ONLY a JSON object, no other text, matching exactly this shape:
{"decision": "same_person" | "different_person" | "needs_human_review",
 "confidence": <float 0.0-1.0>, "reasoning": "<one sentence>"}
```

**User:**
```
Record A (existing, from {record_a.source_system}):
{record_a as JSON}

Record B (incoming, from {record_b.source_system}):
{record_b as JSON}

Context: {context}
```

- Parse the response into `ConflictResolution`. If parsing fails OR
  `confidence < 0.7`, override the decision to `needs_human_review`
  regardless of what Claude returned — never let a low-confidence or
  malformed response silently auto-merge two people.
- `needs_human_review` outcomes: log `NEEDS_HUMAN_REVIEW` to the audit
  log, do not merge, do not propagate that field, and add to
  `needs_attention()`'s output (extend the ledger view or track alongside
  it — either is fine as long as `main.py`'s summary surfaces it).
- `ambiguous_name_conflict.json` (Section 14) is the fixture for this
  path — requires the state store to be pre-seeded with a matching
  existing record first (see Section 17).


## 12. MCP TOOL (stretch — build only after Sections 5-11 work and pass tests)

- Use the official `mcp` Python SDK, stdio transport.
- Entrypoint: `python -m src.mcp_server`.
- Tool name: `resolve_identity_conflict`.
- Input schema: `{record_a: object, record_b: object, context: string}`.
- Output schema: `{decision: string, confidence: number, reasoning: string}`.
- The tool function should be a thin wrapper that constructs `Employee`
  objects from the input dicts and delegates to the same
  `ClaudeHandler.resolve_conflict()` used by `sync_engine.py` — do not
  duplicate the prompt or gating logic.
- Note if using MCP SDK v2: register this as a plain sync tool function —
  the SDK runs sync tools on a worker thread automatically, no async
  wrapper needed.
- Mention explicitly in build_note.md why this is an MCP tool rather than
  a plain function: it lets the exact resolution logic be invoked live
  from Claude Code/Desktop during the debrief.

CLI usage:
```
python -m src.main --event <path> [--data-dir data/] [--dry-run]
  --event      required. Path to a ChangeEvent JSON file.
  --data-dir   optional. Defaults to ./data.
  --dry-run    optional. Runs normalize/validate/diff, prints what WOULD
               be written, makes no connector writes and no state changes.
Exit code 0 if no FAILED or needs_human_review entries resulted, else 1.
```


## 17. TESTING STRATEGY (resolves v1's real-call-vs-CI contradiction)

- Default `pytest` run must NOT require `ANTHROPIC_API_KEY` and must NOT
  hit the network. `test_claude_conflict.py`'s primary test injects a fake
  `anthropic.Anthropic`-shaped client into `ClaudeHandler(client=...)`
  (per Section 8) that returns a canned `same_person`/`needs_human_review`
  response — this proves the confidence-gating and parsing logic without
  spending money or depending on network access.
- Exactly one test is marked `@pytest.mark.integration` and additionally
  wrapped in `@pytest.mark.skipif(not os.environ.get("ANTHROPIC_API_KEY"), ...)`
  — this is the one real call, run manually before the debrief with
  `pytest -m integration`, proving the actual integration works end to
  end against `ambiguous_name_conflict.json`.
- `tests/conftest.py` provides:
  - a `seeded_store` fixture: a `StateStore` pointed at a temp dir,
    pre-populated with `emp_2001` (from `offcycle_hire.json`'s
    raw_payload) — required by `ambiguous_name_conflict.json`'s test.
  - a `no_sleep` fixture: `lambda _: None`, passed as `sleep_fn` to
    `write_with_retry` so the retry tests run instantly.
  - a `fake_anthropic_client` fixture returning a stub with a
    `.messages.create()` method returning a canned response object.

- [ ] Running `name_change.json` twice produces exactly one real write
      per downstream system, proven by `test_idempotency.py`.
- [ ] A forced expoIT failure does not block Workday/Okta writes, proven
      by `test_partial_failure.py`.
- [ ] `offcycle_hire.json` is handled without inventing a fake Ashby
      record, proven by `test_offcycle_backfill.py`.

      pre-seeded `emp_2001`, and does NOT flag unrelated records.
- [ ] `test_claude_conflict.py`'s unit test passes with no network access
      and no `ANTHROPIC_API_KEY`; the integration test passes when run
      manually with a real key.

      to `needs_human_review`, proven by a test with the fake client.
- [ ] A bad field is dropped without dropping the rest of the event.
- [ ] `python -m src.main --event ... --dry-run` makes no writes.
- [ ] `systems_map.md` and `build_note.md` follow the templates in
      Section 19 and are complete.
- [ ] No new third-party infrastructure was added beyond Section 4.
